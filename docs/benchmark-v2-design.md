# Legacy、Single、Multi 对照评测集 v2 设计

状态：设计完成，尚未运行。日期：2026-09-19。

> 历史设计：本页规划过 Legacy/Single/Multi 三方对照。当前 benchmark 阶段已改为只比较 Single/Multi；保留本文供追溯，不作为现行执行参数或结论。

## 目的与边界

v2 用于比较三种运行模式在同一模型配置、同一数据源和隔离请求条件下的结果正确性、完成率、稳定性与延迟。题集仍基于 `sample_data/mf-demo.duckdb`，因此它是语义查询能力的受控对照，不代表跨数据库、跨行业或所有 Agent 能力。

题集文件为 `benchmark/semantic_layer/testing_set_v2.csv`。旧版 `testing_set.csv` 保留，不覆盖历史证据。

## 题集结构

共 24 题，每层 6 题：

| 层级 | 编号 | 主要能力 |
| --- | --- | --- |
| 基础 | B01-B06 | 筛选、计数、去重、分组、Top-N、空结果 |
| 关联 | J01-J06 | 两/三表关联、反关联、条件聚合、比例、分群、组内排名 |
| 时间 | T01-T06 | 完整日期序列、周期比较、滚动/累计窗口、首次事件、日历边界 |
| 复杂 | C01-C06 | 异常检测、事件窗口、类留存、占比、连续日期、复合约束 |

每道题都有稳定 `case_id`、单一主能力标签、无歧义英文题面和可在 DuckDB 执行的参考 SQL。涉及“7 天”时明确写为 calendar days；涉及并列时规定排序；需要零值时明确要求保留零活动对象。

## 运行设计

1. 三种模式必须使用同一底层模型、温度、最大 token、数据源快照和提示词版本；差异只能是运行架构。
2. 每个 `case_id × mode` 至少独立重复 3 次，总请求数为 `24 × 3 × 3 = 216`。每次重复记录随机种子或供应商请求标识（若可用）。
3. 请求顺序采用按重复轮次随机化或拉丁方排列，避免固定顺序把热缓存或服务退化偏向某一模式。
4. 每个请求使用独立会话。超时后必须确认服务端任务停止；无法取消时重启对应服务并通过健康检查后再继续。不同模式不得共享残留任务。
5. 预热请求与正式请求分开，不计入统计。正式运行期间不得修改代码、配置、模型或数据库。
6. 保留所有成功、失败和超时；禁止删除离群点。超时作为未完成，并以超时上限计入截断延迟统计。

## 判分规则

主要正确性采用结果集等价，而不是 SQL 字符串相同：

- 列按语义映射；参考题面明确排序时检查顺序，否则按行集合比较。
- 浮点数使用绝对误差 `1e-6` 与相对误差 `1e-4` 中较大者。
- 日期统一成 ISO 日期；空结果必须返回明确的 0 或空表，依题面和参考结果判定。
- SQL 可执行但结果不等价记为错误；只有解释而没有可核验结果也记为错误。
- 图表题必须至少提供等价数据表；仅有图片不能自动判定正确。

每次请求记录：`case_id`、模式、重复序号、开始/结束时间、完成状态、端到端延迟、生成 SQL、执行结果、错误类型、token 用量（若提供）、人工复核备注。人工复核者在不知道模式名称的情况下处理自动判分无法覆盖的响应。

## 汇总指标

主要指标：整体执行正确率、各层正确率、完成率、三次重复全对率。辅助指标：中位延迟、P95、超时率、SQL 可执行率、同题结果一致率。每个百分比同时报告分子/分母；每种模式总样本为 `n=72`，每层为 `n=18`。

不把 24 题结果表述为产品总体正确率。三模式差异报告配对题目的 bootstrap 置信区间；样本量仍较小，不只依据单一百分比下结论。
