# 前端完整链路测试设计

> 日期：2026-09-23  
> 范围：Single Agent、Multi Agent。`runtime_variant` 只接受 `single` / `multi`，旧运行时值必须被 API 拒绝。

## 目标

验证用户输入经 Agent、SQL 和数据源处理后，后端返回正确结果，且前端能完整呈现并在会话历史中保持一致。本轮仅验收已实现的真实功能，不以静态数据或模拟回答作为通过依据。

## 测试顺序

### 1. 命令行直测后端

- 不启动浏览器，使用 `curl.exe` 或 PowerShell HTTP 命令直连本地 API；检查健康状态、模型和数据目录。
- 对 `POST /api/v1/chat/stream` 分别提交 Single 与 Multi 请求，使用相同的只读问题、隔离测试数据源和不同会话。
- 验证省略 `runtime_variant` 时默认为 `single`；提交 `legacy` 时返回 HTTP 422，且不启动 Agent。
- 收集完整 SSE，确认会话建立、正常结束且没有错误事件；核对生成的 SQL 和回答。通过 `POST /api/v1/sql/execute` 执行固定只读查询，并与测试数据的预期列、行数和值比较。
- 不记录凭据，不写入用户数据。保留命令、模式、脱敏请求要点、SSE 摘要及结果核对记录。

### 2. 前后端完整联通

仅在两种模式的后端直测均通过后，启动测试用 API 和前端。在界面分别选择 Single、Multi，以相同问题创建会话，并核对包括但不限于模式、输入、会话 ID、流式消息、最终回答、SQL 和结果表格。刷新或切换会话后，确认历史与后端一致；对已实现的 SQL 控制台和数据目录读取链路，使用同一测试数据源核对数据。检查浏览器控制台和网络请求，确保失败时显示真实错误。

## 通过标准

- Single 与 Multi 分别完成从输入到回答、SQL 和数据库结果的链路；SQL 结果与隔离测试数据的预期值一致。
- 页面展示、会话历史与后端响应一致，无非预期请求失败、未处理前端错误或测试引发的数据写入。
- 任一阶段失败，先修复并重测该阶段，不开始或不标记后续阶段通过。记录测试数据源、执行命令、模式、结果摘要和失败项；仅清理确认属于本轮测试的会话与产物。
