# Multi-Agent SQL 系统测评计划

## Summary

本计划以 Multi-Agent 为主评测对象，并增加小规模 Single-Agent 基线，用于方向性对照。计划只定义评测方法和报告口径，不包含真实模型/API 请求。

评测规模如下：

- Multi-Agent 正式评测：24 题 × 3 次重复 = 72 次请求。
- Single-Agent 基线：同一 24 题、同一模型和数据配置，各执行 1 次 = 24 次请求。
- 总计：96 次真实请求。

Single-Agent 结果不用于严格统计显著性结论。若后续需要对外声称 Multi-Agent 优于 Single-Agent，应追加 Single-Agent 24 题 × 3 次重复的完整对照。

## Multi-Agent 正式评测

Multi-Agent 正式评测覆盖以下指标：

- Schema Recall@5、MRR、平均检索延迟和 P95 延迟；
- SQL 首次生成正确率；
- 失败 SQL 自动修复成功率和平均修复轮数；
- 语义 Reviewer 错误 SQL 拦截率和误杀率；
- SQL Guard 对危险及非只读语句的拦截率；
- 非法状态迁移拦截率；
- 平均工具调用次数、Token 消耗和单题成本。

所有百分比必须同时报告分子和分母。失败、异常和超时请求不得静默删除，并按对应指标的预先定义计入统计。

### Schema 检索指标

- `Recall@5`：Top-5 结果中命中的 gold 表数量除以该题 gold 表总数，按题目宏平均；
- `MRR`：第一条命中 gold 表的排名倒数，无命中记为 0，按题目宏平均；
- 平均检索延迟：Schema 检索节点从开始到返回的毫秒数；
- P95 延迟：使用统一的最近秩法，并明确是否包含超时样本。

结果应同时提供整体值和基础、关联、时间、复杂四个题型分层值。

### SQL 生成与修复指标

- 首次生成正确：首次 SQL 可执行，且结果集与参考结果等价；
- 首次生成正确率：首次正确题数 / 有效请求总数，失败和超时计入分母；
- 自动修复成功：首次 SQL 失败后，在修复预算内生成可执行且结果等价的 SQL；
- 自动修复成功率：修复成功题数 / 进入修复流程的失败题数；
- 平均修复轮数：仅统计实际进入自动修复流程的请求。

每次请求记录首次 SQL、执行错误、修复 SQL、修复触发原因、修复轮数和每轮耗时。

## Single-Agent 基线

Single-Agent 使用与 Multi-Agent 完全一致的：

- 题集和参考结果；
- 模型、温度和最大 Token；
- 数据库快照；
- 提示词版本和超时配置；
- 请求隔离和判分规则。

两种架构只比较以下共有指标：

- 最终结果正确率；
- 首次 SQL 正确率；
- 自动修复成功率；
- 延迟；
- Token 消耗；
- 工具调用次数；
- 单题成本。

Single-Agent 基线必须标注 `n=24`，并注明每题仅执行 1 次。该结果只用于方向性参考，不用于稳定性、置信区间或统计显著性结论。

## 安全指标

Reviewer、SQL Guard 和状态机安全测试以 Multi-Agent 的完整安全测试集为主：

- Reviewer 错误 SQL 拦截率；
- Reviewer 误杀率；
- SQL Guard 危险及非只读语句拦截率，目标为 100%；
- 非法状态迁移拦截率，目标为 100%。

指标定义如下：

- Reviewer 错误 SQL 拦截率 = 正确拦截的错误 SQL / 错误 SQL 总数；
- Reviewer 误杀率 = 被错误拦截的正确 SQL / 正确 SQL 总数；
- SQL Guard 拦截率 = 成功拦截的危险或非只读样本 / 危险或非只读样本总数；
- 非法状态迁移拦截率 = 被拒绝的非法迁移 / 非法迁移总数。

这些指标属于共享安全边界，不作为 Multi-Agent 与 Single-Agent 的主要架构对比项。如果两种架构实际使用不同安全链路，应分别标记并分别统计。

## 成本与资源消耗

对每个 Multi-Agent 请求记录完整 trace：

- 工具调用次数，包括 Schema、检索、执行、Reviewer、Debugger、Guard 和重试调用；
- 模型服务返回的 prompt、completion 和 total token；
- 输入 Token、输出 Token、工具/执行服务费用及单题总成本；
- 异常请求、重试和超时的资源消耗。

Token 或价格信息缺失时，指标标记为“不可用”，不得推测。价格表、币种和生效日期必须随评测报告保存。

## 结果报告结构

报告按以下顺序输出：

1. Multi-Agent 正式结果；
2. Single-Agent 方向性基线；
3. 两种架构的共同指标差异表；
4. Multi-Agent 安全指标；
5. 成本与资源消耗；
6. 失败、超时和人工复核样本；
7. 样本量、数据源范围和外推限制。

报告必须分别标注 `Multi n=72` 和 `Single n=24`，并明确禁止使用小规模 Single-Agent 基线得出“Multi-Agent 显著优于 Single-Agent”的结论。

## Test Plan

1. 冻结题集、参考结果、模型配置、提示词、数据库快照、价格表和代码提交 ID。
2. 逐题验证参考 SQL，并保存参考结果快照。
3. 验证请求取消、超时和服务重启隔离流程。
4. 先执行少量 Multi-Agent 和 Single-Agent 试运行，确认日志字段、自动判分和成本采集正确。
5. 执行 Multi-Agent 72 次正式请求。
6. 执行 Single-Agent 24 次基线请求。
7. 生成原始 JSONL、汇总 JSON、共同指标对照表和 Markdown 报告。
8. 如果后续需要严格架构对比，再追加 Single-Agent 24 题 × 3 次重复。

## 数据记录要求

每次请求至少记录：

- `case_id`、架构模式、重复序号；
- 开始时间、结束时间、端到端延迟和完成状态；
- 生成 SQL、执行结果、错误类型和修复记录；
- Schema Top-5 结果及检索延迟；
- 工具调用明细、Token 用量和成本；
- 自动判分结果及人工复核备注。

失败、超时和 Guard 拒绝请求必须保留在原始记录中，以支持从原始数据重算全部汇总指标。

## Assumptions

- Multi-Agent 是主验收对象，Single-Agent 是小规模方向性基线。
- 当前计划不包含 Legacy；如需验证相对现有生产链路的收益，再单独增加 Legacy 基线。
- 正确性按参考结果等价判定，而不是 SQL 字符串相等。
- 平均修复轮数仅统计实际进入自动修复流程的失败请求。
- 本计划不执行真实 API 请求。
